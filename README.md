### ไฟล์แนบ (รูปถ่าย · ลายเซ็น)

บน production ใช้ **Supabase Storage** — `.env` ต้องมี:

```
STORAGE_DRIVER="supabase"
SUPABASE_URL="https://<ref>.supabase.co"
SUPABASE_SERVICE_ROLE_KEY="..."      # ห้ามมี NEXT_PUBLIC_ นำหน้า
SUPABASE_STORAGE_BUCKET="work-orders"
```

> ⚠️ **bucket ต้องเป็น private** — key ของไฟล์เดาได้โดยออกแบบ (`yyyymm/entity/id/kind/file`)
> ถ้าเปิด public = ใครก็เปิดดูรูปในบ้านลูกค้าได้ ระบบเสิร์ฟผ่าน signed URL เท่านั้น
>
> ⚠️ **ห้ามใช้ `STORAGE_DRIVER=local` บน Vercel** — ดิสก์เป็น ephemeral รูปที่อัปจะหายทันที
> ในเครื่องตัวเองใช้ `local` ได้ปกติ
>
> ถ้าตั้ง `supabase` แต่ไม่ใส่ URL/KEY **แอปจะไม่ start เลย** ตั้งใจให้ fail ตอน boot
> ไม่ใช่ตอนช่างกดอัปโหลดอยู่บนหลังคา

> ⚠️ **DATABASE_URL ต้องเป็น pooler ไม่ใช่ direct host**
> `db.<ref>.supabase.co` เป็น **IPv6-only** — บางเครือข่าย resolve ไม่ได้เลย
> (อาการคือ `getaddrinfo ENOENT` หรือ `P1001` แบบสุ่ม) และ Vercel ต่อไม่ได้แน่นอน
>
> ```
> aws-0-ap-southeast-1.pooler.supabase.com:5432   ← session mode: dev / migrate / test
> aws-0-ap-southeast-1.pooler.supabase.com:6543   ← transaction mode: บน Vercel
> ```

| แจ้งเตือน | `NotificationChannel` (console ⇄ LINE ⇄ email) | ยังไม่มีสิทธิ์ LINE ก็พัฒนาต่อได้ |

### 3 หน้าจอ

- `src/app/(staff)` — ออฟฟิศ ธุรการ ผู้จ่ายงาน หัวหน้างาน (จอคอมพิวเตอร์)
- `src/app/(tech)` — ช่างภาคสนาม (มือถือ ปุ่มใหญ่ ออกแบบเผื่อไม่มีสัญญาณ)
- `src/app/(portal)` — ลูกค้า จองคิวและติดตามงาน

`prisma/schema/*.prisma` กับ `src/modules/*` จับคู่กัน 1:1

## 3 จุดที่ควรอ่านก่อน

### 1. ระบบโควตา — `src/modules/scheduling/quota.service.ts`

คุมกำลังรับงาน **3 แกนพร้อมกัน**: จำนวนงาน · จำนวนเครื่อง · **นาทีทีมช่าง**

แกนที่สามสำคัญที่สุด เพราะเว็บบริษัทประกาศเวลาทำงานต่อเครื่องไว้ 30/40/60/90 นาที
การกำหนดว่า "วันละ 10 งาน" จึงไม่มีความหมาย — งานล้างแอร์ติดผนัง 10 เครื่อง กับงานแอร์ซ่อนในฝ้า 10 เครื่อง
กินกำลังช่างต่างกันสามเท่า

**หนึ่งช่องต่อ (วัน × เขต × ประเภทงาน)** ไม่แยกตามขนาดงาน เพราะช่างทีมเดียวกันทำทั้งงานเล็กงานใหญ่
ถ้าแยกช่องตามขนาด วันหนึ่งอาจขึ้นว่า "ยังว่าง" สำหรับงานเล็ก ทั้งที่ช่างถูกจองหมดแล้ว

การจองใช้ `SELECT ... FOR UPDATE` ล็อกแถวเดียว ลูกค้าสองคนแย่งคิวสุดท้ายพร้อมกันจะสำเร็จแค่คนเดียว
และมี `CHECK constraint` ในฐานข้อมูลเป็นด่านสอง — ต่อให้โค้ดมีบั๊ก Postgres ก็ไม่ยอมให้รับงานเกิน

### 2. ค่าเข้าตรวจเช็ค — `src/modules/billing/fee.service.ts`

เก็บเป็น **บัญชีเดินสะพัด เขียนเพิ่มอย่างเดียว** ไม่ใช่ตัวเลขที่แก้ทับได้

| เหตุการณ์ | สิ่งที่บันทึก |
|---|---|
| รับงาน ลูกค้าทั่วไป | `+ค่าตรวจเช็ค` |
| รับงาน ลูกค้าในสัญญา | **ไม่บันทึกเลย** ระบุเหตุผลว่ายกเว้นตามสัญญา |
| ลูกค้าไม่ซ่อมต่อ | ค่าตรวจเช็คคงอยู่ ออกบิลตามนั้น |
| ลูกค้าตกลงซ่อม | `+ส่วนลด` (ค่าติดลบ) |

ยอดสุทธิคำนวณจาก `SUM(amountSigned)` เสมอ — ตรวจย้อนหลังได้ และไม่มีทางผิดเพราะมีคนแก้ตัวเลข

### 3. แบบฟอร์มใบงาน — `src/lib/forms/`

ฟอร์มทั้ง 3 ใบเก็บเป็น **ข้อมูลในฐานข้อมูล ไม่ใช่โค้ด** เมื่อลูกค้าส่งฟอร์มจริงมาก็เพิ่มเป็นเวอร์ชันใหม่ได้ทันที

`templateVersion` ถูกบันทึกไว้บนใบงานแต่ละใบ — ใบงานที่ออกปี 2569 จะยังแสดงผลแบบเดิมเสมอ
แม้ฟอร์มจะเปลี่ยนไปแล้วในปี 2570

`Signature.payloadHash` เก็บ SHA-256 ของเนื้อหาตอนที่เซ็น ถ้ามีการแก้ไขภายหลังจะตรวจจับได้
— นี่คือความต่างระหว่าง "รูปลายเซ็น" กับ "หลักฐาน"

### 🔴 เทสต์รันกับฐานข้อมูลเดียวกับที่ลูกค้าใช้จริง

ไม่มี `TEST_DATABASE_URL` แยก — `npm test` ต่อ `DATABASE_URL` ตัวเดียวกับ production
ตอนทะเบียนพนักงานยังว่างมันไม่มีอะไรเสียหาย **ตั้งแต่ 2 ก.ย. ที่ลูกค้ากรอกข้อมูลจริง มันมี**

ทุกคำสั่งลบในเทสต์ถูกกันด้วย prefix แล้ว และตรวจแล้วว่าข้อมูลลูกค้ารอดครบหลังรันชุดเต็ม

| ไฟล์ | prefix ที่ใช้กัน |
|---|---|
| `hr.employee.test.ts` | `TESTEMP-` · `testemp.` |
| `hr.employee-login.test.ts` | `TESTLOGIN-` · `testlogin.` |
| `hr.timeclock.test.ts` | `EMP-TC-` |
| `hr.payroll.test.ts` | `EMP-PAY-` · งวด `2400-` |
| `hr.wage.test.ts` | `TESTWAGE-` |
| `hr.self-service.test.ts` | `CODE_PREFIX` |

**บทเรียนที่ต้องอ่าน** — เดิม `hr.payroll.test.ts` ล้างงวดด้วย `startsWith: '2569-'`
ซึ่งเป็น **ปี พ.ศ. ปัจจุบัน** ไม่ใช่ prefix ของเทสต์ และ `openPeriod()` คืนงวดเดิมถ้ารหัสซ้ำ
แทนที่จะสร้างใหม่ ผลคือทันทีที่ลูกค้าปิดงวด `2569-08` เทสต์จะหยิบงวดจริงมาเขียนทับ
แล้วลบทิ้งตอน cleanUp **ยังไม่เคยระเบิดเพราะยังไม่มีงวดในระบบเลย**
แก้แล้วโดยย้ายไป `2400-` (พ.ศ. ที่ไม่มีวันชนของจริง) วันที่ที่ใช้คำนวณยังเป็นของเดิม

> **prefix ที่ดูเหมือนกันเทสต์ อาจไม่ได้กันอะไรเลย** ถ้าเพิ่มเทสต์ที่ลบข้อมูล
> ให้ถามก่อนว่า prefix นี้มีโอกาสตรงกับข้อมูลจริงของบริษัทไหม

### อย่ารัน vitest ซ้อนกัน

สองรอบพร้อมกันบนฐานเดียวกัน `cleanUp` ของตัวหนึ่งจะลบแถวที่อีกตัวกำลังใช้
อาการคือ `Foreign key constraint violated` ในเทสต์ที่ไม่เกี่ยวอะไรด้วยเลย
เจอมาแล้ว 2 รอบ เสียเวลาไล่หาสาเหตุนาน — **ไม่ใช่บั๊กในโค้ด**

ข้อที่สำคัญที่สุด: **จอง 20 รายการพร้อมกันแย่งคิวสุดท้าย ต้องสำเร็จ 1 รายการเท่านั้น**
การขายคิวเกินคือความผิดพลาดที่ทำให้ระบบนี้เสียหายที่สุด

### เขียนเทสต์ฟอร์มต้องระวัง

`FormRenderer` เขียนลง payload **เฉพาะคีย์ที่ผู้ใช้แตะ** — หมวดที่ช่างไม่เปิดจะไม่มีอยู่เลย

ฟอร์มที่กรอกถูกต้องส่งไม่ผ่าน **สร้าง payload ให้เหมือนที่ renderer ส่งจริงเสมอ**

## ข้อควรรู้สำหรับผู้พัฒนาต่อ

- **ค่าที่ลูกค้ายังไม่ยืนยัน เก็บเป็นข้อมูลในฐานข้อมูล ไม่ฝังในโค้ด** — ดูตาราง `AppConfig`
  และหน้า `/settings/assumptions` แก้ได้โดยไม่ต้องแก้โปรแกรม
- **ชื่อตารางเป็น snake_case แต่ชื่อคอลัมน์เป็น camelCase** (ค่าเริ่มต้นของ Prisma)
  เวลาเขียน SQL ดิบต้องใส่ `"เครื่องหมายคำพูด"` ครอบชื่อคอลัมน์เสมอ
- **คอลัมน์ `@db.Date` เก็บเป็นเที่ยงคืน UTC** ต้องใช้ `dateOnly()` เทียบเสมอ
  ถ้าใช้เที่ยงคืนเวลาไทยจะเลื่อนไปวันก่อนหน้าและหาไม่เจอ (เคยเป็นบั๊กจริงในแอปช่าง)
- **`middleware.ts` รันบน Edge runtime** ห้าม import อะไรที่ใช้ `node:crypto` หรือ Prisma
  ค่าคงที่ที่ใช้ร่วมกันอยู่ใน `src/lib/auth/constants.ts`
- **CSS ที่ต้องชนะ utility ของ Tailwind ต้องอยู่นอก `@layer`** เช่นกฎขอบแดงของฟอร์ม
- **แบบฟอร์มเป็นข้อมูล ไม่ใช่โค้ด** — แก้ `src/lib/forms/templates.ts` แล้ว **ต้อง `npm run db:seed`**
  ไม่งั้นฐานข้อมูลยังเป็นเวอร์ชันเดิม (เคยเป็นบั๊กจริง: โค้ดมีใบซ่อม v2 แต่ DB มีแค่ v1
  ใบงานที่ช่างกรอกจะได้ฟอร์มร่างแทนฟอร์มบริษัท)
- **seed ปลดระวางแถวที่หายจากลิสต์ให้อัตโนมัติ** — `seedCatalog()` ปิด `isActive` ของ
