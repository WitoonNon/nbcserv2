`Technician` ชี้มาหาผ่าน `employeeId` ไม่เก็บซ้ำจนข้อมูลเพี้ยนกันเอง

#### 🔐 ข้อนี้ยกระดับความอ่อนไหวของข้อมูลทั้งระบบ — อ่านให้ครบก่อนแก้

ก่อนหน้านี้ระบบเก็บข้อมูลลูกค้า ตอนนี้เก็บ **เลขบัตรประชาชน เลขบัญชีธนาคาร เงินเดือนรายคน**
คนละชั้นกันตาม PDPA

**กติกา 5 ข้อ ห้ามแก้โดยไม่เข้าใจว่าทำไม**

1. **เลขบัตร/เลขบัญชี เข้ารหัส AES-256-GCM** (`src/lib/crypto/field.ts`)
   IV สุ่มใหม่ทุกค่า — ถ้าใช้ IV ซ้ำ คนที่เห็นตารางจะบอกได้ว่าพนักงาน 2 คนใช้บัญชีเดียวกัน
   โดยไม่ต้องถอดรหัสเลย · GCM ไม่ใช่ CBC เพราะ **ค่าที่ถูกแก้ในฐานข้อมูลต้องถอดไม่ออก
   ไม่ใช่ถอดออกมาเป็นค่าอื่น**
2. **เก็บ 4 หลักท้ายไว้แบบอ่านได้** เพื่อให้ค้นหาและยืนยันกับสมุดบัญชีได้ โดยเลขเต็มไม่ต้องขึ้นจอ
3. **การอ่านปกติไม่คืนข้อมูลอ่อนไหว ทุกระดับสิทธิ์** ถ้าคืนมาโดยอัตโนมัติ
   เดี๋ยวมันไปโผล่ในหน้า list ในล็อก ในแคช แล้วการเข้ารหัสก็ไม่มีความหมาย
4. **`viewSensitive()` เขียนล็อกก่อนถอดรหัส และ `await`** ถ้าเขียนล็อกไม่ได้ = ไม่ให้ข้อมูล
   การอ่านแฟ้มพนักงานที่ไม่ถูกบันทึกคือสิ่งที่ trail นี้มีไว้กันโดยตรง
5. **สิทธิ์แยก 3 ชั้น** `employee.read` / `.write` / `.sensitive`
   หัวหน้าช่างควรรู้ว่าลูกทีมเริ่มงานเมื่อไหร่ แต่**ไม่ควรเห็นว่าใครได้เงินเท่าไหร่**

> **ช่องกรอกเลขบัตรที่ว่างเปล่าตอนแก้ไข = "ไม่แก้ของเดิม" ไม่ใช่ "ลบทิ้ง"**
> ฟอร์มแสดงค่าที่เก็บไว้ไม่ได้ (ต้องถอดรหัส ซึ่งจะทำให้การแก้เบอร์โทรกลายเป็นการอ่านเลขบัตร)
> ช่องว่างจึงเป็นสภาพปกติของการกดบันทึกทั่วไป · มีเทสคุมข้อนี้

#### 🔑 `FIELD_ENCRYPTION_KEY` — ตั้งแล้ว 26 ส.ค. 2569

ตั้งบน Vercel production แล้ว **ใช้คีย์เดียวกับที่อยู่ใน `.env` ของเครื่องพัฒนา
เพราะทั้งสองชี้ไปที่ฐานข้อมูล Supabase ตัวเดียวกัน** — หนึ่งฐานข้อมูล หนึ่งคีย์
ถ้าใช้คนละคี้ ข้อมูลที่กรอกจากเครื่องพัฒนาจะอ่านไม่ได้บน production และกลับกัน

```bash
# ถ้าต้องตั้งใหม่ในอนาคต
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
npx vercel env add FIELD_ENCRYPTION_KEY production --value "<คีย์>"
npx vercel --prod --yes   # env ใหม่ไม่มีผลกับ deployment เดิม ต้อง deploy ซ้ำ
```

- **คีย์อยู่กับเจ้าของโปรเจกต์** ดึงกลับจาก Vercel ไม่ได้ · ทีมที่ต้องรันเครื่องตัวเอง
  ต้องขอคีย์ไปใส่ `.env` ไม่ใช่สร้างใหม่
- **คีย์หาย = ข้อมูล 2 คอลัมน์นั้นอ่านไม่ได้ตลอดกาล** ไม่มีทางกู้ ออกแบบมาแบบนั้น
- **เปลี่ยนคีย์ = ข้อมูลเก่าอ่านไม่ได้** ตอนนี้ยังไม่มีข้อมูลจริงสักแถว เปลี่ยนได้ฟรี
  พอลูกค้ากรอกเลขบัตรจริงไปแล้วจะเปลี่ยนไม่ได้อีก
- **ถ้าไม่มีคีย์ `/employees` จะพังทันทีที่เปิด** — เป็นความตั้งใจ โค้ด throw
  ดีกว่าเผลอเก็บเลขบัตรแบบไม่เข้ารหัสโดยไม่มีใครรู้

### ✅ ประวัติการปรับค่าแรง — ทำเสร็จแล้ว

`src/modules/hr/wage.service.ts` · ตาราง `employee_wage_changes`

ลูกค้าขอมาเป็น *"หมายเหตุ กรณีปรับค่าแรง"* แต่ทำเป็น**ตาราง**ไม่ใช่ช่องหมายเหตุ

```ts
await wageAtDate(employeeId, วันในงวดนั้น)

```

**กติกาที่ฝังไว้**
- `wageAtDate` คืน **null** ถ้ายังไม่เคยตั้งค่าแรง — ระบบเงินเดือนต้องอ่านว่า
  "คำนวณไม่ได้" **ห้ามตีความเป็นศูนย์**
- **ย้อนหลังใส่รายการเก่าได้ โดยไม่ทับค่าแรงปัจจุบัน** — คนลืมบันทึกการปรับเมื่อ มี.ค.
  แล้วมาใส่ทีหลัง ต้องไม่ไปลบการปรับของ ก.ย.
- `previousRate` เก็บ**ค่าที่มีผลจริง ณ วันนั้น** ไม่ใช่ค่าปัจจุบัน ไม่งั้นการขึ้นเงินเดือน
  จะแสดงเป็นการลด
- **ลบได้เฉพาะรายการล่าสุด** รายการเก่าอาจถูกใช้คำนวณเงินไปแล้ว
  การแก้ฐานของเงินที่จ่ายไปแล้วแย่กว่าการปล่อยแถวที่ดูแปลก
- เก็บ `employmentType` คู่กับเรทเสมอ — 500/วัน กับ 18,000/เดือน เทียบกันไม่ได้

**งานที่ยังเหลือจากคำตอบข้อ 3** — อัปโหลดสำเนาบัตร/ทะเบียนบ้าน/วุฒิการศึกษา

### เหลือทำในกอง 10,000

| งาน | หมายเหตุ |
|---|---|
| ลงเวลาเข้า-ออก (QR ปริ๊น + GPS) | ค่า config พร้อมแล้ว |
| ขออนุมัติโอที | ยืมสายอนุมัติจากใบงาน |
| ขอลา | นโยบายพร้อมแล้ว |
| คำนวณเงินเดือน | พร้อมเริ่ม |
| อัปโหลดเอกสารพนักงาน | ลูกค้าขอ 26 ส.ค. |

**กติกาที่ตกลงไว้แล้ว อย่าตัดออกเพื่อลดราคา**

1. **ตัวกันโกงคือ GPS ไม่ใช่ QR** — QR ติดผนังถูกถ่ายรูปส่งไลน์กลุ่มภายในวันแรก
2. **QR ทำ 2 แบบในราคาเดียว** พิมพ์ติดผนัง (token ถาวร) + แสดงบนจอ (token 30 วิ) · **แจ้งลูกค้าไปแล้ว**
3. **GPS ไม่ขึ้น = ลงเวลาได้ แต่ติดธงให้หัวหน้าตรวจ** พนักงานต้องไม่เสียสิทธิ์เพราะมือถือ
4. **เรทโอทีต่ำกว่ากฎหมายไม่ได้** 1.5 / 2 / 3 เท่า — ระบบต้องกันไว้
5. **ปิดรอบแล้วล็อก** เงินเดือนที่ย้อนไปแก้ได้เงียบๆ คือตัวเลขที่ตรวจสอบไม่ได้

### ⬜ สลิปเงินเดือน PDF — ลูกค้าขอเพิ่ม 25 ส.ค.

ต้นทุนต่ำ เครื่องมือมีครบจาก 2.4 (`print.css` · หน้า A4 · `PrintButton`)
แต่ **ต้องผูกกับกติกาข้อ 5 — ออกได้เฉพาะรอบที่ปิดแล้ว** สลิปที่พนักงานถือคือหลักฐานการจ่ายเงิน
ถ้าตัวเลขยังแก้ย้อนหลังได้หลังพิมพ์ สลิปกับระบบจะไม่ตรงกัน

> ⚠️ สลิปต้องเขียนกำกับว่า**ยังไม่ได้หักประกันสังคมและภาษี** ไม่งั้นพนักงานอ่านยอดนั้นว่าคือเงินที่ได้รับจริง

### 💰 เรื่องเงินที่ทีมต้องรู้

**สลิปเงินเดือน PDF และ ทะเบียนประวัติพนักงาน อยู่ในรายการ "ไม่รวมในรอบนี้"
ของใบเสนอราคา 10,000 ที่ลูกค้ารับไปแล้ว** — เขียนชื่อไว้ตรงตัวทั้งคู่

อย่าไปคุยกับลูกค้าว่ารวมอยู่แล้ว

## 4. ชั้น raw SQL — ของใหม่ ควรใช้

`src/lib/db/sql.ts`

Prisma ตอบคำถามส่วนใหญ่ได้ดี แต่บางคำถามเป็นของฐานข้อมูล — จัดกลุ่มงานทั้งปีเป็นรายเดือน
ตามเวลาไทย รวมโควตาข้ามโซน ล็อกแถว **raw SQL จึงเป็นเครื่องมือหลัก ไม่ใช่ทางหนี**

```ts
import { query, queryOne, queryValue, sql, all, inList } from '@/lib/db/sql';

const rows = await query<{ month: Date; jobs: number }>(
  sql`SELECT date_trunc('month', "createdAt") AS month, COUNT(*) AS jobs
        FROM "jobs" WHERE ${all([
          sql`"status" <> 'CANCELLED'`,
          zoneId ? sql`"zoneId" = ${zoneId}` : null,
        ])}
       GROUP BY 1`,
  { name: 'jobsByMonth' },
);
```

**3 กับดักที่ชั้นนี้ปิดให้**

1. **BigInt** — `COUNT`/`SUM` คืน bigint และ **`JSON.stringify` throw** ส่งจาก server component
   ไป client แล้วหน้าขาวทั้งหน้า · แปลงให้อัตโนมัติ และ**ปฏิเสธถ้าค่าใหญ่เกินจะแปลง**
   แทนที่จะปัดเศษเงียบๆ (คืนเลขผิดแยกไม่ออกจากทำงานปกติ)
2. **เงื่อนไขที่มีบ้างไม่มีบ้าง** — `all` `any` `inList` · `IN ()` ว่างเป็น syntax error → คืน FALSE
3. **มองไม่เห็นว่า query ไหนช้า** — Prisma มี log ของมัน raw SQL ไม่มี · ตอนนี้มีชื่อ + เวลา เตือนเกิน 250ms

> **ค่าที่ interpolate เข้าไปเป็น bind parameter เสมอ** ไม่ใช่การต่อสตริง
> ยกเว้น `raw()` ที่แปะข้อความตรงๆ — **ห้ามให้ค่าจากผู้ใช้เข้าใกล้มัน**

### 📌 บันทึกความเข้าใจผิดที่แก้แล้ว

comment เดิมใน `quota.service.ts` เขียนว่าการจองล่มเพราะ nested `Prisma.sql` ใน tagged template
กลายเป็น bind parameter · **การจองล่มจริงและแก้แล้วหายจริง แต่กลไกที่บันทึกไว้ไม่ตรง**
ทดสอบบน `@prisma/client 7.9.1` แล้ว — nested fragment, `Prisma.empty`, `Prisma.raw`
ทำงานถูกต้องทั้ง tagged form และ argument form

มีเทสตรึงพฤติกรรมนี้ไว้ใน `tests/db.sql.test.ts` ถ้าอัปเกรดแล้วพังจะรู้ทันที
**สิ่งที่ป้องกันการจองจริงๆ คือเทสที่ครอบทั้งกรณีมีและไม่มี optional condition** —
บั๊กเดิมรอดมาได้เพราะไม่มีเทสไหนส่ง argument ที่ทำให้ branch นั้นทำงาน

## 5. เรื่อง performance — วัดแล้ว อย่าเดา

มีคำถามว่าเว็บกิน CPU หนักไหม **วัดแล้วไม่ใช่**

```
VS Code (7 process)   ~38,800 วินาที
Chrome (3 process)    ~17,000 วินาที
node ทั้งหมดรวมกัน          72 วินาที   ← dev server 60 วินาที ใน 16 นาที
```

**และ Prisma 7 ไม่มี Rust query engine แล้ว** — ต่อผ่าน `@prisma/adapter-pg`
ยิง `pg` ตรงๆ เหมือน Drizzle ทำ · เหตุผลเดิมที่คนหนีจาก Prisma ไม่มีอยู่ในโปรเจกต์นี้
**จึงไม่ควรเพิ่ม ORM ตัวที่สอง** — จะได้ schema 2 ที่ migration 2 ระบบ query 2 สไตล์
โดยไม่ได้ความเร็ว

**ของที่ช้าจริงมี 2 อย่าง ถ้าจะ optimise ให้เริ่มจากนี่**

1. `force-dynamic` **30 หน้า** — ไม่ cache อะไรเลย · แต่เป็น latency ไม่ใช่ CPU
   และหน้าจ่ายงาน/ตารางงานต้องสดจริง เลือกเป็นหน้าๆ
2. **กราฟ 1.4 MB** — CPU ฝั่ง client ตอนวาด canvas · ถ้าจะลด ลดที่จำนวนกราฟ

## 6.1 ❓ คำถามค้างเรื่องสิทธิ์ — อย่าเดา ให้ถามลูกค้า

ตอนนี้ **ธุรการ (ADMIN) เปิดหน้า `/employees` ไม่ได้เลย** — ไม่มีสิทธิ์ `employee.read`

| บทบาท | เห็นทะเบียนพนักงาน | เห็นเงินเดือน/เลขบัญชี | เพิ่ม-แก้ไข |
|---|---|---|---|
| SUPER_ADMIN (เจ้าของ) | ✅ | ✅ | ✅ |
| SUPERVISOR | ✅ | ❌ | ❌ |
| ACCOUNTING | ✅ | ❌ | ❌ |
| **ADMIN (ธุรการ)** | **❌** | ❌ | ❌ |

ลูกค้าตอบแค่ว่า **เงินเดือนและเลขบัญชี** เจ้าของดูคนเดียว **ไม่ได้บอกว่าธุรการห้ามเห็น
ทะเบียนพนักงานทั้งหมด** ตอนนี้ตั้งไว้แบบแคบที่สุดไว้ก่อน ซึ่งปลอดภัยแต่แปลว่า
**มีแต่เจ้าของที่เพิ่มพนักงานเข้าระบบได้**

ถ้าออฟฟิศเป็นคนกรอกข้อมูลพนักงาน ต้องให้ `employee.read` + `employee.write` กับ ADMIN
(ยังไม่เห็นเงินเดือนอยู่ดี เพราะแยกเป็น `employee.sensitive`) — **ถามลูกค้าก่อนเปลี่ยน**

## 7. กับดักที่เคยกัดมาแล้ว — อย่าเหยียบซ้ำ

| เรื่อง | สิ่งที่เกิดขึ้น |
|---|---|
| **Vercel region** | ฟังก์ชันอยู่ `iad1` DB อยู่สิงคโปร์ → ทุกหน้า 1.7–5 วิ · แก้เป็น `sin1` เหลือ 0.4–0.6 วิ |
| **push แล้วไม่ deploy** | Vercel **ไม่** auto-deploy · ต้อง `npx vercel --prod --yes` |
| **`npm run lint` ใช้ไม่ได้** | เรียก `next lint` ที่ถูกถอดใน Next 16 · ยังไม่ได้ย้ายไป ESLint CLI |
| **`after()` นอก request scope** | โมดูล domain ห้ามพึ่ง request context ของ Next · เรียกที่ route boundary |
| **เทสยิง LINE จริง** | pin driver ใน `vitest.config.ts` แล้ว |
| **`new Date('2026-08-25')`** | คือ UTC เที่ยงคืน = ไทย 7 โมงเช้า · ใช้ `dateOnly()` หรือแยก parts เอง |
| **deleteMany ไม่ใส่ filter** | Prisma ตีความว่า "ทุกแถว" · เคยลบข้อมูลเกินที่ตั้งใจมาแล้ว · ทุก cleanup ในเทสมี guard |
| **seed เดิมเพิ่มสิทธิ์อย่างเดียว ไม่เคยถอด** | ลบ permission ออกจาก `ROLE_PERMISSIONS` แล้ว**ไม่มีผลกับ DB ที่มีอยู่** โค้ดบอกอย่าง ระบบทำอีกอย่าง เงียบสนิท · เจอตอนถอด `employee.sensitive` จาก ACCOUNTING · **แก้แล้ว** seed prune ให้ตรงลิสต์ |
| **`import 'server-only'` ทำ seed พัง** | ไม่ใช่แพ็กเกจที่ติดตั้ง — Next bundler เป็นคนแก้ให้ · `tsx` ที่รัน seed หาไม่เจอ · โมดูลใต้ `lib/db/` ที่ seed/script ใช้ **ห้ามใส่** |
