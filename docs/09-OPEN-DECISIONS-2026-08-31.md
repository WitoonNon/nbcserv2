### 🔴 `FIELD_ENCRYPTION_KEY` ไม่มีใน `.env` ของเครื่องนี้เลย

มีแต่ใน [`.env.example:73`](.env.example) — ตัว `.env` จริงไม่มีบรรทัดนี้

[`src/lib/crypto/field.ts:36`](src/lib/crypto/field.ts:36) โยน error ทันทีถ้าไม่มีคีย์
(`refusing to store personal data unencrypted` — fail safe ไม่ใช่ fail open)
แปลว่าหน้าไหนที่แตะ **เลขบัตรประชาชน · เลขบัญชีธนาคาร** จะพังทันทีที่ต่อ DB ได้

**ต้องเป็นคีย์เดียวกับที่ใช้เข้ารหัสข้อมูลในฐานใหม่** คนละคีย์ = AES-256-GCM
decrypt ไม่ผ่าน = ข้อมูลพนักงานที่เข้ารหัสไว้อ่านไม่ออกถาวร
(GCM authenticate ด้วย จึงไม่ decrypt ออกมาเป็นขยะเงียบ ๆ — มันฟ้อง)

## 3. 🔴 พิกัดจุดสแกน — 2 คำถาม + 1 งานมือ

### 3.1 คำถามที่ต้องได้จากลูกค้า

**จุดที่ติด QR อยู่ที่ไหนกันแน่**

| ที่อยู่ | ที่มา |
|---|---|
| 74/1 หมู่ 3 ต.ละหาร | ลูกค้าแจ้งเอง 26 ส.ค. |
| 105/26 หมู่ 2 ต.ละหาร | ที่อยู่จดทะเบียน · พิมพ์บนหัวใบงาน |

สองที่นี้ **ห่างกัน 1.38 กม.** ซึ่งเกินรัศมีทุกแบบ — เดาไม่ได้ ต้องถาม

**และขอพิกัดจริง** ไปยืนที่จุดติด QR เปิดแผนที่บนมือถือ อ่านค่ามา
ตอนนี้ค่าที่ใช้เป็นแค่จุดกึ่งกลางหมู่บ้านจาก OpenStreetMap (OSM ไม่มีเลขที่บ้านแถบนี้)

### 3.2 งานมือที่ต้องทำใน DB จริง — ยังไม่ได้ทำ

**seed ไม่เขียนทับ `value` ของเดิม** (ตั้งใจ — ค่าที่ออฟฟิศแก้ต้องไม่หาย)
**ฐานข้อมูลจริงจึงยังเป็นค่าเก่าที่ผิด 4.8 กม.**

ไปแก้เองที่ **`/settings/assumptions`**

| key | ค่าที่ต้องเป็น |
|---|---|
| `office.location.lat` | `13.9391592` |
| `office.location.lng` | `100.4379344` |
| `office.location.radiusMetres` | `1500` (ชั่วคราว) |

ระยะที่วัดเมื่อ 31 ส.ค. ด้วย `distanceMetres()`:

| จาก | ถึง | ระยะ |
|---|---|---|
| พิกัดเดิมใน DB (ศูนย์กลางตำบล) | หมู่ 3 | **4.84 กม.** |
| พิกัดเดิมใน DB | หมู่ 2 | **5.33 กม.** |

**ถ้าปล่อยไว้:** รัศมี 300 ม. ห่างจริง 4.8 กม. → **ลงเวลาติดธงทุกครั้ง**
ซึ่งแย่กว่าไม่ตรวจเลย เพราะคิวที่เต็มตลอดคือคิวที่ไม่มีใครอ่าน

### 3.3 พอได้พิกัดจริงแล้ว — ลดรัศมีทันที

`1500` ม. ตั้งไว้ให้ตรงกับความไม่แน่นอนจริง ไม่ใช่แกล้งทำเป็นแม่นกว่าที่เป็น
กันสแกนจากบ้านได้ **แต่กันสแกนจากร้านข้าง ๆ ไม่ได้**

**ได้พิกัดจริงเมื่อไหร่ → ลดเหลือ 50–100 ม. ทันที** ไม่งั้นการตรวจนี้แทบไม่มีความหมาย

## 4. 🟡 ม.62 โอทีวันหยุด — จ่ายเกินที่กฎหมายบังคับ

[`src/modules/hr/payroll-rules.ts:51`](src/modules/hr/payroll-rules.ts:51)

```ts
export const LEGAL_MINIMUM_MULTIPLIER: Record<OvertimeKind, number> = {
  WORKDAY_OT: 1.5,   // ม.61 — ถูกต้อง
  HOLIDAY_WORK: 2,   // ม.62 — ตรงนี้แหละ
  HOLIDAY_OT: 3,     // ม.63 — ถูกต้อง
};
```

**กฎหมายว่าไว้:** ม.62 แยกตามว่าลูกจ้างได้ค่าจ้างวันหยุดนั้นอยู่แล้วหรือเปล่า

| กลุ่ม | ขั้นต่ำตามกฎหมาย | ที่โค้ดจ่าย |
|---|---|---|
| **รายเดือน** (ได้ค่าจ้างวันหยุดอยู่แล้ว) | เพิ่ม **1 เท่า** | 2 เท่า |
| **รายวัน** (ไม่ได้ค่าจ้างวันหยุด) | เพิ่ม **2 เท่า** | 2 เท่า ✅ |

**ไม่ผิดกฎหมาย** — สูงกว่าขั้นต่ำไม่เคยผิด และลูกค้าระบุ 1.5 / 2 / 3 มาเอง
**แต่จ่ายพนักงานรายเดือนเกินที่บังคับ** ซึ่งเป็นเงินจริงทุกวันหยุด

**ต้องการ:** ยืนยันว่าตั้งใจให้เท่ากันหมด หรือให้แยกตามกฎหมาย
ถ้าให้แยก — แก้ที่เดียวคือค่าคงที่ข้างบน + ให้ `overtimeAmount()` รับ `employmentType`
เข้ามาตัดสิน (basis มีอยู่แล้ว ไม่ต้องเปลี่ยน signature)

## 5. 🟡 ประกันสังคม + ภาษี — ยอดสุทธิยังไม่ใช่ยอดจริง

[`src/modules/hr/payroll-rules.ts:210`](src/modules/hr/payroll-rules.ts:210)

`netSatang` = ฐาน + โอที + รายการเพิ่ม − รายการหัก
**ยังไม่หักประกันสังคมและภาษีหัก ณ ที่จ่าย** เพราะยังไม่ได้อัตรามาจากลูกค้า
และการเดาอัตราตามกฎหมายแย่กว่าการไม่แสดงเลย

**ความเสี่ยงตอนนี้:** พนักงานอ่านตัวเลขนี้เป็นยอดที่จะเข้าบัญชี แล้วมันไม่ใช่

**ต้องได้จากบัญชี/ลูกค้า:**
- อัตราสมทบประกันสังคม + เพดานฐานค่าจ้าง
- วิธีคำนวณภาษีหัก ณ ที่จ่าย (คำนวณเอง หรือใช้ยอดคงที่ที่บัญชีส่งมา)
- มีกองทุนสำรองเลี้ยงชีพหรือหักอื่น ๆ อีกไหม

**ระหว่างที่ยังไม่ได้:** ทุกหน้าที่แสดงยอดนี้ต้องเขียนกำกับว่า *ก่อนหักประกันสังคมและภาษี*
ก่อนออกสลิปให้พนักงานเห็นจริง

  ใช้ Edit/Write เท่านั้น · ตรวจด้วย `Select-String -Pattern 'à¸'`
- **`npm install` ทุกครั้งหลัง pull**
- **Vercel ไม่ auto-deploy** — ต้อง `npx vercel --prod --yes`
- **`deleteMany` ต้องมี filter เสมอ** — ไม่ใส่ = ทุกแถว เคยลบเกินมาแล้ว
- **`new Date('2026-08-25')`** = UTC เที่ยงคืน = ไทย 7 โมงเช้า · ใช้ `dateOnly()`
