## 🆕 อัปเดตจากลูกค้า 9 ส.ค. 2569 — ความหมายของราคาเปลี่ยน

ลูกค้าตอบคำถามเรื่องช่วงราคาแล้ว และ**คำตอบไม่ตรงกับที่เราตีความไว้เดิม**

> ราคา 900–1,100 / 500–650 / 800–1,100 **หมายถึงราคาขึ้นอยู่กับหน้างาน
> ความยากง่าย ความสูง และจำนวนรวม เช่นจำนวนเยอะราคาก็จะต่ำลง**

เดิมระบบตีความว่าเป็น **ราคา 2 ระดับ (ลูกค้าในสัญญา / ลูกค้าทั่วไป)** ซึ่งผิด
ถ้าปล่อยไว้ ระบบจะคิดเงินลูกค้าในสัญญาเลขต่ำเสมอ และลูกค้าทั่วไปเลขสูงเสมอ ทุกงาน

**แก้แล้ว:**

| เดิม | ใหม่ |
|---|---|
| `priceContract` / `priceStandard` | `priceMin` / `priceMax` (migration `20260809000000_catalog_price_range`) |
| `resolvePrice()` คืน `unitPrice` ตัวเดียวตาม tier | คืน **ช่วงราคา** ไม่คืนตัวเลขเดียว โดยตั้งใจ |
| หน้าจอง: "ลูกค้าในสัญญาได้ราคาพิเศษ" | "ราคาขึ้นกับสภาพหน้างาน ความยากง่าย ความสูง และจำนวนเครื่อง" |
| `/settings/pricing` หัวคอลัมน์ "ในสัญญา / ทั่วไป" | "ราคาต่ำสุด / ราคาสูงสุด" + คำอธิบาย |
| เปลือยซ่อนฝ้า = รอราคา | **800–1,100** |

⚠️ **ห้ามเขียนโค้ดที่เดาตัวเลขเดียวจากช่วงนี้** — ปัจจัยที่ใช้ตัดสิน (ความสูง ความยาก จำนวน)
เป็นดุลพินิจหน้างาน ไม่ใช่ข้อมูลที่ระบบมี ราคาจริงต้องมาจากการเสนอราคาของเจ้าหน้าที่

**ยังต้องถามลูกค้าต่อ (`@client-confirm D6`):** ส่วนลดตามจำนวนคิดยังไง —
กี่เครื่องขึ้นไปลดเท่าไหร่ ถ้าได้ขั้นบันไดมาถึงจะทำให้ระบบคำนวณเองได้

`PricingTier` (CONTRACT/STANDARD) ยังอยู่ในระบบ เพราะยังใช้ตัดสิน**สิทธิ์ตรวจเช็คฟรี**

## 1.1 · หน้าตั้งค่าโควตา — `/settings/quota` ✅ จุดขายหลัก

**ทำไมต้องมาก่อนหน้าจองคิว:** ปฏิทินจองคิวจะแสดงวันว่างได้ ต้องมี `QuotaDay` ก่อน
ซึ่งเกิดจาก `materialiseQuota()` ซึ่งอ่านจาก `QuotaRule` — ถ้าตั้งกฎไม่ได้ ปฏิทินก็ว่างเปล่า

**ทำไมสำคัญที่สุด:** ลูกค้าถามข้อนี้เป็นคำถามแรกตอนขาย
("กำหนดได้ไหมว่าวันหนึ่งรับได้กี่เคส งานเล็ก 3 งานใหญ่ 1–2")
ถ้าเดโมแล้วโชว์หน้าจอนี้ไม่ได้ = เสียจุดขายหลัก

### ทำแล้ว

| ส่วน | ไฟล์ |
|---|---|
| `createQuotaRule()` · `updateQuotaRule()` · `deactivateQuotaRule()` | `schedule.service.ts` |
| หน้าตารางกฎ + ฟอร์มแก้ไข (ประเภทงาน · เขต · วันในสัปดาห์ · 3 แกน · ช่วงวันที่ · ลำดับ) | `settings/quota/page.tsx` · `QuotaRuleManager.tsx` |
| ปุ่ม **คำนวณปฏิทินใหม่** → `materialiseQuota()` 90 วัน | `settings/quota/actions.ts` |
| **แก้โควตาเฉพาะวันเดียว** ที่ `/schedule` → `setDayCapacity()` | `schedule/actions.ts` · `QuotaCalendar.tsx` |

**กติกาที่ฝังไว้ในโค้ด:**
- กฎที่ไม่กำหนดสักแกนถูกปฏิเสธ — ไม่งั้นวันนั้นจะรับงานไม่จำกัดทั้งที่ดูเหมือนมีเพดาน
- กฎถูก **ปิดการใช้งาน ไม่ลบทิ้ง** — ไม่งั้นจะอธิบายไม่ได้ว่าทำไมวันในอดีตมีความจุเท่านั้น
- ลดเพดานต่ำกว่างานที่จองแล้ว **ไม่ยกเลิกงานเดิม** แค่หยุดขายเพิ่ม (งานสัญญากับลูกค้าไปแล้ว)
- ทุกการแก้รายวันเขียน `QuotaOverrideLog` พร้อมเหตุผลและผู้ทำ

### จุดที่ต้องระวังตอนอธิบายลูกค้า

ระบบ **ไม่แยกช่องตามขนาดงาน** — จงใจ ดูเหตุผลใน `scheduling.prisma:47-53`
"งานใหญ่รับได้ 1–2 เคส" เกิดจากแกน **นาทีทีมช่าง** ไม่ใช่ช่องแยก

ตัวอย่างที่ควรใช้เดโม — ตั้ง `maxTechnicianMinutes = 480`:

| งาน | คำนวณ | ผล |
|---|---|---|
| ล้างแอร์ติดผนัง 30 นาที/เครื่อง | 480 ÷ 30 | รับได้ 16 เครื่อง |
| แอร์ซ่อนในฝ้าใหญ่ 90 นาที/เครื่อง | 480 ÷ 90 | รับได้ 5 เครื่อง |
| งานโรงงาน 40 เครื่อง × 90 นาที | 3,600 > 480 | **เคสเดียวเต็มวัน** |

**คำที่ควรใช้:** "ระบบคิดจากกำลังช่างที่ใช้จริง" — ไม่ใช่ "แยกช่องเล็ก/ใหญ่"

**เกณฑ์ว่าเสร็จ:** แอดมินตั้ง "จันทร์-ศุกร์ ล้าง-PM รับ 8 งาน / 480 นาที" ได้จากหน้าเว็บ
กดคำนวณปฏิทิน แล้วหน้า `/booking` แสดงวันว่างตามนั้นทันที

## 1.2 · หน้าจองคิวลูกค้า — `/booking` ✅

ขั้นตอน: เลือกงาน → เลือกวัน → ยืนยันค่าตรวจเช็ค → จองสำเร็จ

| ทำแล้ว | รายละเอียด |
|---|---|
| เลือกประเภทงาน · ประเภทเครื่อง · จำนวนเครื่อง | ปฏิทินคำนวณใหม่ทุกครั้ง — งาน 40 เครื่องกับ 1 เครื่องมีวันว่างไม่เหมือนกัน |
| ปฏิทิน **แยกรายเดือน + ปุ่มเลือกเดือน** | เปิดเต็ม 90 วันตาม `QUOTA_HORIZON_DAYS` · แต่ละปุ่มบอกว่าเดือนนั้นว่างกี่วัน |
| เลือกวัน → `holdSlot()` | กันคิว 10 นาทีระหว่างกรอกข้อมูล |
| **หน้ายืนยันค่าตรวจเช็ค** | `previewInspectionFee()` · ลูกค้าในสัญญาขึ้น "ยกเว้นตามสัญญา" · **ไม่ติ๊กยอมรับ = จองไม่ได้** |
| ยืนยันจอง → `createJobFromBooking()` | เรียก `bookSlotWithin()` **ในทรานแซกชันเดียวกับการสร้าง Job** |
| หน้าสำเร็จ + ลิงก์ไปหน้าติดตาม | แสดงเลขที่งาน |

> ⚠️ **กติกาที่ห้ามพัง:** `createJobFromIntake()` **ไม่กินโควตา** โดยตั้งใจ (งานรับทางโทรศัพท์

> ถ้าเผลอเอา intake มาใช้กับการจองเว็บ = ขายคิวเกิน มี `tests/booking.quota.test.ts` เฝ้าไว้แล้ว

**ทดสอบแล้ว:** จอง 10 รายการพร้อมกันแย่งคิวสุดท้าย → สำเร็จ 1 · งานใหญ่ 3,600 นาทีถูกปฏิเสธ

### กติกาที่ฝังไว้ อย่าเผลอแก้ทิ้ง

1. **บัคเก็ตเป็น private เสมอ** — ชื่อไฟล์เดาได้โดยตั้งใจ (`yyyymm/WorkOrder/<id>/BEFORE/<uuid>.jpg`)
   ดังนั้น "รู้ชื่อไฟล์" ต้องไม่พอที่จะเปิดดู ทุกการเข้าถึงผ่าน `/api/media/...` ที่เช็ค session
   หรือเป็น signed URL อายุสั้นเท่านั้น (ทดสอบแล้ว: ไม่มี session ได้ **401**)
2. **ชื่อไฟล์ที่ผู้ใช้ส่งมาถูกทิ้งทั้งหมด** — ระบบตั้งชื่อเป็น UUID เอง
   `mediaKey()` ยังกรองทุก segment อีกชั้น เพราะ local driver เอา key ไปต่อเป็น path จริง
3. **แนบรูปได้เฉพาะใบงานที่ยัง DRAFT หรือ RETURNED** — ใบที่ส่งแล้วคือของที่หัวหน้างานกำลังดูอยู่
   ชุดรูปต้องไม่เปลี่ยนใต้มือเขา
4. **เอารูปออกจากฟอร์ม = ลบ key ออกจาก payload เท่านั้น** แถว `Attachment` กับไฟล์ยังอยู่
   หลักฐานการไปหน้างานไม่ควรหายเพราะกดพลาด (ค่าใช้จ่ายคือไฟล์กำพร้าไม่กี่ KB)
5. **อัปโหลดทีละรูป แต่ละรูป commit แยกกัน** — เน็ตหลุดตอนรูปที่ 4 ต้องไม่ทำให้ 3 รูปแรกหาย

### EXIF — อ่านเก็บไว้ก่อนย่อรูป

canvas ลบ EXIF ทิ้งตอน re-encode ระบบจึง **อ่านก่อน** แล้วส่งมาเป็น field แยก
`Attachment.exifTakenAt` / `lat` / `lng` มีค่าจริงแล้ว

`src/lib/media/exif.ts` เป็น parser เขียนเอง อ่านแค่ 4 แท็ก (DateTimeOriginal + GPS 4 ตัว)
ไม่เพิ่ม dependency · รองรับทั้ง little-endian และ big-endian · มี 10 เทสต์ใน `media.exif.test.ts`
ที่ประกอบไฟล์ JPEG ขึ้นมาทีละไบต์

**ข้อจำกัดที่ต้องพูดตรง ๆ กับลูกค้า:** ค่านี้มาจาก client จึงเป็น "สิ่งที่กล้องอ้าง" ไม่ใช่หลักฐานที่ปลอมไม่ได้
ทางเลือกเดียวที่แข็งกว่านี้คือส่งไฟล์ต้นฉบับขึ้นมาให้เซิร์ฟเวอร์อ่าน ซึ่งขัดกับเหตุผลที่ย่อฝั่ง client
ตั้งแต่แรก (รูปกล้อง 4–8 MB ต่อรูป บนเน็ตมือถือ)

ฝั่งเซิร์ฟเวอร์กรองค่าที่เป็นไปไม่ได้ทิ้ง — พิกัดเกินขอบเขตโลก · เวลาถ่ายในอนาคต ·
**พิกัดมาไม่ครบคู่ทิ้งทั้งคู่** เพราะครึ่งเดียวจะวางหน้างานไว้บนเส้นศูนย์สูตร ซึ่งแย่กว่าไม่รู้

### รูปย่อ (thumbnail)

canvas ตัวเดียวกันเข้ารหัสสองขนาดจากการ decode ครั้งเดียว — 1600px สำหรับเก็บ
และ 320px สำหรับแสดงผล เก็บเป็น `Attachment.thumbKey` ชื่อไฟล์อนุมานจากไฟล์เต็ม (`.thumb.jpg`)

payload ยังเก็บ key เดียวต่อรูปเหมือนเดิม — เรียกรูปย่อด้วย `?thumb=1`
รูปที่อัปโหลดไว้ก่อนมีฟีเจอร์นี้จะได้ไฟล์เต็มแทน ไม่ 404

*วัดจริง: รูป 2400×1600 → เต็ม 14,496 bytes · ย่อ 2,002 bytes (320×213)*

### ทำแล้ว

### กติกาที่ฝังไว้ อย่าเผลอแก้ทิ้ง

1. **hash คำนวณตอนเซ็น ไม่ใช่ตอนส่ง** — ถ้าไป hash ตอนส่ง มันจะครอบคลุมข้อความที่พิมพ์เพิ่ม
   *หลังจาก* ลูกค้าเซ็นไปแล้ว ซึ่งคือสิ่งที่ hash มีไว้จับพอดี
2. **payload ถูกเขียนและถูก hash ในทรานแซกชันเดียวกัน** — hash จึงครอบเนื้อหาที่ระบบเก็บจริง
   ไม่ใช่เนื้อหาที่ client อ้างว่าอยู่บนจอ
3. **ไม่มีชื่อ เซ็นไม่ได้** — ลายเซ็นที่ไม่ระบุว่าใครเซ็นคือของประดับ ไม่ใช่หลักฐาน
   (ชื่อดึงจากช่อง `ชื่อ` ในหมวดเดียวกันตามข้อตกลงชื่อคีย์: `inspectorSignature` ↔ `inspectorName`)
4. **เซ็นซ้ำ = แทนที่ของเดิม ไม่ใช่ต่อคิว** — ใบร่างที่แก้แล้วเซ็นใหม่ต้องมีความจริงชุดเดียว
5. **ใบที่ส่งหรืออนุมัติแล้วเซ็นเพิ่มไม่ได้** — จะเปลี่ยนสิ่งที่หัวหน้างานกำลังตรวจอยู่

### การแก้หลังเซ็นถูก "จับได้" ไม่ใช่ "ห้าม"

แก้ฟอร์มหลังเซ็นแล้ว **ยังส่งได้** แต่จะมีแถบเตือนขึ้นทั้งหน้าและที่ช่องลายเซ็นนั้นโดยตรง
ซึ่งหัวหน้างานเห็นด้วยตอนตรวจ (หน้า readOnly ก็ยังแสดงคำเตือน)

เลือกทางนี้เพราะการบล็อกจะทำให้ช่างที่แก้คำผิดตอนสี่ทุ่มหลังลูกค้ากลับไปแล้วติดตาย
ส่วนการเตือนให้ข้อมูลกับคนที่ตัดสินใจได้ — หัวหน้างานตีกลับเองได้ถ้าไม่โอเค

> ถ้าภายหลังลูกค้าอยากให้บล็อกจริง ๆ เพิ่มเช็คใน `submitWorkOrder()` ได้เลย
> ข้อมูลที่ต้องใช้มีครบแล้ว — เทียบ `payloadHash(payload)` กับแถว `Signature`

### ยังไม่ได้ทำในข้อนี้

- ยังไม่มีบทบาท `SUPERVISOR` บนฟอร์มจริง — ใบซ่อม v2 มีแค่ช่องผู้ตรวจรับ (CUSTOMER)
  กับผู้ซ่อมบำรุง (TECHNICIAN) โค้ดรองรับครบ 3 บทบาทแล้ว รอฟอร์มที่มีช่องหัวหน้างาน

### วิธีที่เลือก — หน้าเอกสาร A4 + สั่งพิมพ์จากเบราว์เซอร์

เบราว์เซอร์เรนเดอร์ไทยถูกอยู่แล้ว และเราฝัง Sarabun ไว้เองด้วย (`src/lib/fonts.ts`

กด "บันทึกเป็น PDF" ในกล่องพิมพ์ได้ทั้ง Chrome / Edge / Safari รวมถึงบนมือถือ

**ข้อ 4 "เก็บไฟล์ไว้เปิดย้อนหลังได้" ได้อยู่แล้ว — และดีกว่าเก็บไฟล์ PDF จริง ๆ**

ถ้าเก็บเป็น PDF blob แทน ไฟล์กับฐานข้อมูลจะเริ่มไม่ตรงกันวันใดวันหนึ่ง และเปลืองที่เก็บกว่ามาก

> ⚠️ **สิ่งที่วิธีนี้ยังทำไม่ได้ — พูดตรง ๆ ไว้ก่อน**
> แนบ PDF ส่งเข้า LINE หรืออีเมลแบบอัตโนมัติไม่ได้ ต้องมีคนกดพิมพ์
> ถ้าเฟส 3 ต้องส่งอัตโนมัติ ค่อยเติม Chromium ทีหลัง **โดยไม่ต้องรื้อตัวเอกสาร**

### 🟡 ข้อ 2 offline — เปลี่ยนสถานะกับรูปถ่ายทำได้แล้ว

**สิ่งที่รอดเมื่อสัญญาณหลุด:** กดปุ่มเปลี่ยนสถานะ · ถ่ายรูปแนบใบงาน
เก็บลง IndexedDB แล้วส่งเองเมื่อกลับมาออนไลน์ · หน้าจอบอกว่ามีกี่รายการค้างอยู่

| ไฟล์ | หน้าที่ |
|---|---|
| `src/lib/offline/outbox.ts` | คิว FIFO · กติกาว่าอะไร retry อะไรทิ้ง (ไม่ผูกกับ IndexedDB) |
| `src/lib/offline/indexeddb-store.ts` | ที่เก็บจริง — IndexedDB เพราะต้องเก็บ Blob รูป |
| `src/lib/offline/client.ts` | outbox ตัวจริง · sender ต่อชนิด · `submitOrQueue` |
| `src/components/tech/OutboxIndicator.tsx` | "มี N รายการรอส่ง" · แตะเพื่อลองส่งเดี๋ยวนี้ |
| `src/app/api/field/advance/route.ts` | endpoint สำหรับ replay (server action replay ไม่ได้) |
| `tests/offline.outbox.test.ts` · `offline.contracts.test.ts` | 22 เทสต์ |

**กติกาที่ฝังไว้:**

1. **ส่งตามลำดับที่เกิดจริง และหยุดที่ตัวแรกที่ล้ม** — รูปต้องถึงก่อนใบงานที่อ้างถึงรูปนั้น
   ถ้าปล่อยให้ตัวหลังแซง ใบงานจะไปถึงพร้อม key ที่เซิร์ฟเวอร์ไม่เคยเห็น
2. **"ไม่รู้ว่าเกิดอะไรขึ้น" = เก็บงานไว้** — sender ที่ throw ถือเป็นสัญญาณหลุด ไม่ใช่การปฏิเสธ
3. **5xx/408/429 = ลองใหม่ · 4xx อื่น = เลิก** — งานที่ออฟฟิศปิดไปแล้วจะ retry ตลอดกาลถ้าไม่แยก
4. **ออนไลน์ก็เดินผ่านคิวเหมือนกัน** — เส้นทางที่ทำงานเฉพาะตอนพังคือเส้นทางที่ไม่มีใครเคยทดสอบ
5. **`occurredAt` คือเวลาที่กด** ไม่ใช่เวลาที่คิวระบาย

### 🔑 สองข้อตกลงที่ทำให้ offline ปลอดภัย

ทั้งคู่คือกรณีที่ **client กับ server ต้องได้คำตอบเดียวกัน โดยไม่ได้คุยกัน**
ถ้าเพี้ยน ความเสียหายจะเงียบ

**1. ชื่อไฟล์รูป — client เป็นคนตั้ง**

รูปที่ถ่ายตอนไม่มีสัญญาณต้องถูกอ้างใน payload ทันที ทั้งที่ยังไม่มีเซิร์ฟเวอร์เห็น
ถ้าให้เซิร์ฟเวอร์ตั้งชื่อทีหลังแล้วมาแก้ payload ตอน sync **hash ของลายเซ็นทุกใบจะพัง**

- client สร้าง UUID เอง ส่งมาพร้อม `capturedAt`
- เซิร์ฟเวอร์ตรวจรูปแบบ UUID · ปฏิเสธถ้า key นั้นมีของอยู่แล้วและ**เนื้อไฟล์ต่างกัน**
  (ส่งซ้ำจาก sync ที่รันสองรอบเป็นเรื่องปกติ ทับของเดิมคือทับหลักฐาน)
- โฟลเดอร์เดือนคิดจาก `capturedAt` แบบ **UTC** — มือถืออยู่เวลาไทย เซิร์ฟเวอร์อยู่ UTC
  ถ้าใช้เวลาท้องถิ่นคนละฝั่ง รูปเดียวจะไปอยู่คนละโฟลเดอร์
- ฟังก์ชันเดียวกันทั้งสองฝั่ง: `src/lib/media/key.ts`

**2. hash ของลายเซ็น — client คำนวณตอนเซ็น**

`payloadHash()` ย้ายไป `src/lib/forms/payload-hash.ts` ใช้ **Web Crypto** จึงรันได้ทั้งสองฝั่ง
เป็น implementation เดียว — ถ้ามีสองอัน วันที่มันไม่ตรงกันคือวันที่ลายเซ็นทุกใบกลายเป็น "ถูกแก้"

- เบราว์เซอร์ hash ตอนลูกค้ายกนิ้ว แล้วส่ง `signedHash` + `signedAt` ขึ้นมา
- เซิร์ฟเวอร์ hash payload ที่กำลังจะบันทึก แล้วเทียบ **ไม่ตรง = ปฏิเสธ**
- `signedAt` เชื่อ client เท่าที่สมเหตุสมผล (ไม่อนาคต ไม่เกิน 7 วัน) เพราะ offline
  มันคือบันทึกเดียวของเวลาจริง แต่นาฬิกาเครื่องเพี้ยนต้องไม่ทำให้ลายเซ็นไปโผล่เดือนหน้า
- **ออนไลน์ก็ส่ง hash มาด้วยทุกครั้ง** เส้นทาง offline จึงถูกทดสอบทุกการเซ็น

### ⬜ ยังไม่ได้ทำในข้อ 2

| เรื่อง | ทำไม |
|---|---|
| **บันทึกร่างใบงาน + ลายเซ็น ยังต้องมีสัญญาณ** | ยังผ่าน server action ซึ่ง replay จากคิวไม่ได้ ต้องทำ `/api/work-orders/draft` กับ `/sign` ก่อน แล้วสลับ `WorkOrderEditor` มาใช้ `submitOrQueue` (แกน hash พร้อมแล้ว) |
| **เปิดแอปตอนไม่มีสัญญาณไม่ได้** | ยังไม่มี service worker · ตอนนี้ "offline" แปลว่า *แท็บที่เปิดค้างไว้แล้ว* ยังกดงานต่อได้ ถ้ารีโหลดตอนไม่มีเน็ตจะเป็นหน้า error ของเบราว์เซอร์ |
| **รูปที่ยังไม่อัปโหลดไม่แสดงรูปย่อ** | payload มี key แล้วแต่ไฟล์ยังอยู่ในเครื่อง · ต้องอ่าน Blob จากคิวมาแสดงเป็น object URL |

> ⚠️ **อย่าเผลอโฆษณาเกินจริง** — ข้อความบนหน้าจอตอนนี้พูดเฉพาะสิ่งที่ทำได้จริง
> ถ้าเพิ่ม service worker แล้วค่อยเปลี่ยนคำ

3. **เข้า AuditLog** — ใครซ่อน ตอนไหน เพราะอะไร
4. **ห้ามซ่อนรูปที่ทำให้ `minCount` ของ photoGroup ไม่ครบ** ไม่งั้นใบงานที่ผ่านการตรวจแล้วกลายเป็นใบที่ไม่ผ่านเกณฑ์ย้อนหลัง

### เหตุผลที่ไม่ทำแบบลบจริง

วันที่มีข้อพิพาทกับลูกค้าปลายทาง — "ช่างไม่ได้ล้างจริง" — รูปคือหลักฐานฝั่งบริษัท

**ความเสี่ยงตกที่ลูกค้าเอง ไม่ใช่ที่เรา**

# งานเพิ่มเติม — ระบบลงเวลาและสรุปเงินเดือน

> **ใบเสนอราคาแยกฉบับ 10,000 บาท** ไม่ได้อยู่ใน 13,000 ของระบบแจ้งซ่อม
> ตกลงกับลูกค้าเมื่อ 20 ส.ค. 2569 · แบ่งจ่าย 50% มัดจำ / 50% ส่งมอบ
> **ส่งมอบพร้อมงานเฟส 3** — แชร์ตารางเวลา ไม่แชร์ขอบเขตและไม่แชร์เงิน

คำว่า "ส่งมอบพร้อมกัน" ต้องไม่ถูกอ่านว่า "รวมอยู่ในราคาเดิม" ทุกครั้งที่พูดถึงเรื่องนี้กับลูกค้า
ต้องมีประโยคที่แยกค่าใช้จ่ายกำกับอยู่ด้วย

|---|---|
| 1 | **ลงเวลาเข้างาน** สแกน QR ที่ออฟฟิศ ระบุจุดสแกนได้ — *"ลงเวลาต้องสแกนที่ออฟฟิศ"* |

## ของที่มีอยู่แล้วและช่วยให้เร็วขึ้น

ระบบสิทธิ์ผู้ใช้ · การเก็บพิกัด GPS (`field-work.service.ts`) · สายอนุมัติ
(ยืมรูปแบบจากใบงาน `SUBMITTED → APPROVED`) · ระบบแนบไฟล์ · การพิมพ์ PDF (2.4) ·
หน้าจอมือถือของช่าง · `dateOnly()` และวันที่ พ.ศ.

**แต่ที่มีอยู่ไม่ใช่ตอกบัตร** — `JobStatusEvent` บันทึกเวลาที่ผูกกับ **ตัวงาน**
(ออกเดินทาง/ถึงหน้างาน/เริ่ม/ปิด) ส่วนตอกบัตรผูกกับ **การเข้า-ออกที่ทำงาน**
คนละแกนกัน ใช้แทนกันไม่ได้ ต้องสร้างตารางใหม่

> ⚠️ ในอัปเดตที่ส่งลูกค้าเขียนว่า *"เป็นฐานที่ต่อยอดไปเป็นระบบตอกบัตรได้เลย"*
> ซึ่งจริง แต่เปิดช่องให้เข้าใจว่าใกล้เสร็จแล้ว ถ้าถูกถาม ให้ตอบด้วยตารางข้างบน

## กติกาที่ต้องฝังไว้ตั้งแต่ออกแบบ

1. **ตัวกันโกงคือ GPS ไม่ใช่ QR** — QR ติดผนังถูกถ่ายรูปส่งไลน์กลุ่มภายในวันแรก
   ถ้าไม่ตรวจพิกัดควบคู่ ระบบไร้ค่าตั้งแต่วันติดตั้ง ข้อนี้ตัดออกเพื่อลดราคาไม่ได้
2. **QR ทำ 2 แบบในราคาเดียว** — พิมพ์ติดผนัง (token ถาวร) และแสดงบนจอ
   (token อายุ 30 วิ) เข้าหน้าสแกนเดียวกัน ต่างกันแค่ตัว token · **แจ้งลูกค้าไปแล้ว**
3. **GPS ไม่ขึ้น = ลงเวลาได้ แต่ติดธงให้หัวหน้าตรวจ** — เหตุผลเดียวกับ
   `field-work.service.ts` ข้อ 3: พนักงานต้องไม่เสียสิทธิ์เพราะมือถือ
4. **ลงเวลาออกแบบหมุดอิสระต้องมีคนรับรอง** — ถ้ากดปิดที่ไหนก็ได้แล้วนับเป็นเงินทันที
   จะถูกใช้ผิดภายในเดือนแรก
5. **เรทโอทีตั้งต่ำกว่ากฎหมายไม่ได้** — 1.5 เท่าวันปกติ / 2 เท่าวันหยุด / 3 เท่า OT วันหยุด
   ระบบต้องกันไว้ ไม่งั้นเราสร้างเครื่องมือให้ละเมิดกฎหมายแรงงาน
6. **ปิดรอบแล้วล็อก** — เงินเดือนที่ย้อนกลับไปแก้ได้เงียบ ๆ คือตัวเลขที่ตรวจสอบไม่ได้
7. **สิทธิ์เงินเดือนต้องแยกจากของเดิมทั้งหมด** — ตอนนี้ ADMIN เห็นทุกอย่าง
   ปล่อยแบบเดิม = ธุรการเห็นเงินเดือนทุกคนรวมถึงเจ้าของ

# สิ่งที่ผู้พัฒนาต่อต้องรู้

- **ค่าที่ลูกค้ายังไม่ยืนยัน เก็บเป็นข้อมูล ไม่ฝังในโค้ด** — ตาราง `AppConfig`
  และหน้า `/settings/assumptions` แก้ได้โดยไม่ต้องแก้โปรแกรม
- **ชื่อตารางเป็น snake_case แต่ชื่อคอลัมน์เป็น camelCase** — SQL ดิบต้องใส่ `"quotes"` ครอบชื่อคอลัมน์
- **`@db.Date` เก็บเป็นเที่ยงคืน UTC** — ใช้ `dateOnly()` เทียบเสมอ
- **`middleware.ts` รันบน Edge runtime** — ห้าม import `node:crypto` หรือ Prisma
- **CSS ที่ต้องชนะ Tailwind ต้องอยู่นอก `@layer`**
- **ห้ามแยกโควตาตามขนาดงาน** — ดูเหตุผลใน `scheduling.prisma:47-53`
  ถ้าแยก วันหนึ่งจะขึ้นว่า "ว่าง" สำหรับงานเล็ก ทั้งที่ช่างถูกจองหมดแล้ว
- **การจองต้องกินโควตาเสมอ** — `createJobFromIntake()` ไม่กินโควตาโดยตั้งใจ
  ห้ามเอาไปใช้กับการจองผ่านเว็บ ใช้ `createJobFromBooking()` แทน
  (`tests/booking.quota.test.ts` คุมไว้แล้ว)
- **`where: { field: undefined }` ใน Prisma แปลว่า "ไม่กรองเลย" ไม่ใช่ "ไม่ตรงอะไร"**
  เทสต์ที่ teardown ด้วย `deleteMany({ where: { zoneId } })` โดย `zoneId` ยังไม่ถูกเซ็ต
  จะลบ **ทุกแถวในตาราง** — เคยเกิดจริง ปฏิทินโควตาหายทั้งตาราง
  ตอนนี้ teardown ทั้งสองไฟล์มี `if (zoneId)` ครอบแล้ว
- **`npm run dev` วัด performance ไม่ได้** — ต้อง `npm run build && npm run start`
- **เทสต์ฟอร์มต้องผ่าน `FormRenderer` จริง** — payload ที่สร้างด้วยมือพิสูจน์ได้แค่ว่า
  validator ตรงกับตัวเอง บั๊กรูปร่าง payload หลุดมาแล้วสองครั้งด้วยเหตุผลนี้
  ไฟล์ `.test.tsx` รันบน jsdom ผ่าน docblock `@vitest-environment jsdom`
- **โมดูลฝั่งเซิร์ฟเวอร์ที่ import `server-only` ต้องมี alias ใน `vitest.config.ts`** —
  แพ็กเกจจริงจะ throw ทันทีที่ถูก import นอก Next (Next สลับให้เป็นโมดูลว่างผ่าน
  export condition `react-server`) ตอนนี้ alias ไปที่ `tests/stubs/server-only.ts`
