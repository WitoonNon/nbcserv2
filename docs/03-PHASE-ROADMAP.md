## 1.1 · หน้าตั้งค่าโควตา — `/settings/quota` 🔴 จุดขายหลัก

**ทำไมต้องมาก่อนหน้าจองคิว:** ปฏิทินจองคิวจะแสดงวันว่างได้ ต้องมี `QuotaDay` ก่อน
ซึ่งเกิดจาก `materialiseQuota()` ซึ่งอ่านจาก `QuotaRule` — ถ้าตั้งกฎไม่ได้ ปฏิทินก็ว่างเปล่า

**ทำไมสำคัญที่สุด:** ลูกค้าถามข้อนี้เป็นคำถามแรกตอนขาย
("กำหนดได้ไหมว่าวันหนึ่งรับได้กี่เคส งานเล็ก 3 งานใหญ่ 1–2")
ถ้าเดโมแล้วโชว์หน้าจอนี้ไม่ได้ = เสียจุดขายหลัก

### สถานะปัจจุบัน

| ส่วน | สถานะ |
|---|---|
| เครื่องยนต์โควตา 3 แกน | ✅ ครบ · `quota.service.ts` |
| `materialiseQuota()` แปลงกฎ → ช่องรายวัน | ✅ มีแล้ว |
| `getQuotaRules()` | ⚠️ **อ่านอย่างเดียว** · `schedule.service.ts:109` |
| สร้าง / แก้ / ลบ QuotaRule | ❌ **ไม่มีทั้ง service และ UI** |
| แก้ capacity เฉพาะวันเดียว | ❌ มีแค่เปิด-ปิดวัน · `schedule/actions.ts` |

### ต้องทำ

1. `createQuotaRule()` · `updateQuotaRule()` · `deactivateQuotaRule()` ใน `schedule.service.ts`
2. หน้า `/settings/quota` — ตารางกฎ + ฟอร์มแก้ไข
   - เลือกประเภทงาน (ตรวจเช็ค / ล้าง-PM / ซ่อม / ติดตั้ง)
   - เลือกเขต · เลือกวันในสัปดาห์ (`weekdayMask` เป็น checkbox 7 ช่อง)
   - ใส่ 3 แกน: จำนวนงาน · จำนวนเครื่อง · นาทีทีมช่าง (เว้นว่าง = ไม่จำกัด)
   - ช่วงวันที่มีผล + ลำดับความสำคัญ
3. **ปุ่ม "คำนวณปฏิทินใหม่"** → เรียก `materialiseQuota()` 90 วันข้างหน้า
   ต้องมีข้อความเตือนว่าตัวเลขที่ใช้ไปแล้วจะไม่ถูกแตะ (ซึ่งโค้ดทำถูกอยู่แล้ว)
4. **แก้ capacity รายวัน** ที่หน้า `/schedule` — เพิ่ม `setDayCapacity()`
   ทุกครั้งต้องเขียน `QuotaOverrideLog` พร้อมเหตุผลและผู้ทำ (เหมือน `setDayStatus` ที่มีอยู่)

### จุดที่ต้องระวังตอนอธิบายลูกค้า

ระบบ **ไม่แยกช่องตามขนาดงาน** — จงใจ ดูเหตุผลใน `scheduling.prisma:47-53`
"งานใหญ่รับได้ 1–2 เคส" เกิดจากแกน **นาทีทีมช่าง** ไม่ใช่ช่องแยก

ตัวอย่างที่ควรใช้เดโม — ตั้ง `maxTechnicianMinutes = 480`:

| งาน | คำนวณ | ผล |
|---|---|---|
| ล้างแอร์ติดผนัง 30 นาที/เครื่อง | 480 ÷ 30 | รับได้ 16 เครื่อง |
| แอร์ซ่อนในฝ้าใหญ่ 90 นาที/เครื่อง | 480 ÷ 90 | รับได้ 5 เครื่อง |
| งานโรงงาน 40 เครื่อง × 90 นาที | 3,600 > 480 | **เคสเดียวเต็มวัน** |

**คำที่ควรใช้:** "ระบบคิดจากกำลังช่างที่ใช้จริง" — ไม่ใช่ "แยกช่องเล็ก/ใหญ่"

**เกณฑ์ว่าเสร็จ:** แอดมินตั้ง "จันทร์-ศุกร์ ล้าง-PM รับ 8 งาน / 480 นาที" ได้จากหน้าเว็บ
กดคำนวณปฏิทิน แล้วหน้า `/booking` แสดงวันว่างตามนั้นทันที

## 1.2 · หน้าจองคิวลูกค้าให้จบ — `/booking` 🔴

### สถานะปัจจุบัน

`booking/page.tsx` เป็น **server component ล้วน** — ปุ่มทุกปุ่มกดแล้วไม่มีอะไรเกิดขึ้น

| ปัญหา | บรรทัด |
|---|---|
| เลือกประเภทงานไม่ได้ — ไฮไลต์ `i === 0` ตายตัว | `page.tsx:62-66` |
| ปฏิทินอ่าน `CLEANING_PM` ตายตัว ไม่เปลี่ยนตามที่เลือก | `page.tsx:27` |
| กดเลือกวันแล้วไม่เกิดอะไร — ไม่มี state ไม่มี action | `page.tsx:94-121` |
| ไม่มีขั้นตอนกรอกข้อมูลลูกค้า | — |
| ไม่มีหน้ายืนยันค่าตรวจเช็ค | — |

### ต้องทำ

1. แยกเป็น client component — เก็บ state: ประเภทงาน → จำนวนเครื่อง → วันที่
2. ปฏิทินโหลดใหม่เมื่อเปลี่ยนประเภทงาน/จำนวนเครื่อง
   (ส่ง `requiredUnits` / `requiredMinutes` จริงเข้า `getAvailability()`)
3. **เลือกวันแล้วจับจอง** → `holdSlot()` ล็อกอ่อน 10 นาที กันคนอื่นแย่ง
4. **หน้ายืนยันค่าตรวจเช็ค** — เรียก `resolveFeePolicy()` แสดงจำนวนเงิน
   ลูกค้าต้องกดยอมรับก่อนถึงจองได้ (**ตรงนี้คือสิ่งที่สัญญากับลูกค้าไว้**)
   ลูกค้าในสัญญา → แสดง "ยกเว้นตามสัญญา" ไม่คิดเงิน
5. **ยืนยันจอง** → `bookSlot()` + สร้าง Job **ในทรานแซกชันเดียวกัน**
   > ⚠️ `createJobFromIntake()` ที่มีอยู่ **ไม่กินโควตา** (ตั้งใจ — งานรับทางโทรศัพท์
   > ให้ผู้จ่ายงานจัดคิวทีหลัง) ห้ามเอามาใช้ตรงๆ ต้องเขียน `createJobFromBooking()` ใหม่
   > ที่เรียก `bookSlot()` ด้วย ไม่งั้นลูกค้าจองผ่านเว็บจะไม่ตัดโควตา = ขายคิวเกิน
6. หน้าสำเร็จ — แสดงเลขงาน + ลิงก์ไปหน้าติดตาม
7. ยกเลิก/เปลี่ยนวัน → `releaseSlot()` คืนโควตา

**เกณฑ์ว่าเสร็จ:** จองจากหน้าเว็บได้จริง 1 รายการ แล้ว `usedJobs` ในตาราง `quota_days` เพิ่มขึ้น 1
และเมื่อจองจนเต็ม วันนั้นต้องเปลี่ยนเป็น "เต็ม" กดไม่ได้ทันที

# เฟส 2 — เริ่มเมื่อลูกค้าคอนเฟิร์มฟอร์มจริง

> **ตัวปลดล็อกเฟส 2 = ฟอร์มจริงอีก 2 ใบ**
> ได้ใบซ่อมมาแล้ว (ทำเป็น v2 ตรงต้นฉบับเรียบร้อย) เหลือใบตรวจเช็ค/แจ้งซ่อม และใบล้าง/PM
> **ยิ่งได้เร็ว เฟส 2 ยิ่งเริ่มได้เร็ว** — ควรทวงตั้งแต่ตอนนี้

## 2.0 · รับฟอร์มจริง 2 ใบ

| ใบงาน | code | เวอร์ชัน | สถานะ |
|---|---|---|---|
| ใบตรวจเช็ค / แจ้งซ่อม | `INSPECTION_REQUEST` | v1 | โครงร่าง — **รอฟอร์มจริง** |
| ใบล้าง / PM | `CLEANING_PM` | v1 | โครงร่าง — **รอฟอร์มจริง** |
| ใบซ่อม | `REPAIR` | **v2** | ✅ ตรงต้นฉบับแล้ว |

ฟอร์มเก็บเป็น**ข้อมูล ไม่ใช่โค้ด** (`src/lib/forms/templates.ts`)
พอได้ฟอร์มจริงมา เพิ่มเป็น v2 ได้เลย **ไม่ต้องแก้โปรแกรม ไม่ต้อง migrate**

`templateVersion` ถูกบันทึกบนใบงานแต่ละใบ — ใบที่ออกปี 2569 จะแสดงผลแบบเดิมเสมอ
แม้ฟอร์มเปลี่ยนไปแล้วในปี 2570

**พร้อมกันนี้ควรขอ: โลโก้ไฟล์เวกเตอร์** — ที่ใช้อยู่เป็น PNG ความละเอียดต่ำจากเว็บ
พิมพ์ลง PDF แล้วไม่คมชัด **ต้องได้ก่อนทำข้อ 2.4**

## 2.1 · บันทึกใบงานลงฐานข้อมูล

ตอนนี้แสดงฟอร์มได้ แต่ปุ่มบันทึกปิดอยู่

1. `saveWorkOrder()` — เก็บคำตอบเป็น JSONB พร้อมล็อก `templateVersion`
2. สถานะใบงาน `DRAFT → SUBMITTED → APPROVED / RETURNED` (enum มีแล้ว)
3. หัวหน้างานอนุมัติ / ตีกลับ พร้อมเหตุผล

## 2.2 · แนบรูปถ่าย

`StorageAdapter` ยังเป็น stub — แนะนำ **Supabase Storage** เพราะใช้โปรเจกต์เดียวกับ DB อยู่แล้ว

1. เขียน adapter จริง (โครง local ⇄ s3 มีแล้ว ไม่ต้องออกแบบใหม่)
2. อัปโหลดจากมือถือ — ย่อรูปฝั่ง client ก่อนส่ง (ช่างใช้เน็ตมือถือ)
3. จัดหมวดรูปตาม `AttachmentKind` ที่มีแล้ว: ก่อนซ่อม · หลังซ่อม · จุดเสีย · เพลทเครื่อง · ซีเรียล
4. รูปหลายรูปต่อใบงาน

## 2.3 · ลายเซ็น

1. Canvas เซ็นด้วยนิ้วบนมือถือ
2. บันทึก `Signature.payloadHash` = SHA-256 ของเนื้อหาตอนเซ็น
   **นี่คือความต่างระหว่าง "รูปลายเซ็น" กับ "หลักฐาน"** — แก้ทีหลังจะตรวจจับได้
3. 3 บทบาท: ลูกค้า · ช่าง · หัวหน้างาน (enum `SignerRole` มีแล้ว)

## 2.4 · Export PDF ภาษาไทย 🔴 สัญญากับลูกค้าไว้แล้ว

พิสูจน์เทคนิคแล้วว่าทำได้ด้วย **Chromium + ฟอนต์ Sarabun**

1. เรนเดอร์ใบงานเป็น PDF ตรงตามฟอร์มต้นฉบับ **พร้อมปริ้นได้ทันที**
2. ฝังรูปถ่าย + ลายเซ็นลงในเอกสาร
3. ดาวน์โหลด / ส่งอีเมล / ส่งลิงก์ให้ลูกค้า
4. เก็บไฟล์ไว้เปิดย้อนหลังได้

> ตอนขายบอกลูกค้าว่า "ใบงานรวมอยู่ในฟังก์ชัน export แล้ว ราคาเท่าเดิม"
> — ข้อนี้จึงเป็น **ภาระผูกพัน ไม่ใช่ของแถม**

## 2.5 · แอปช่างภาคสนาม

1. ช่างกรอกใบงานจากมือถือได้จริง
2. **ทำงานตอนไม่มีสัญญาณ** แล้ว sync ทีหลัง (ฟอนต์โฮสต์เองไว้แล้วเพื่อข้อนี้)
3. ปุ่มเปลี่ยนสถานะ: ออกเดินทาง → ถึงหน้างาน → กำลังทำ → เสร็จ

> ⚠️ **บั๊กที่เคยเกิดจริง:** คอลัมน์ `@db.Date` เก็บเป็นเที่ยงคืน **UTC**
> ต้องใช้ `dateOnly()` เทียบเสมอ ถ้าใช้เที่ยงคืนเวลาไทยจะเลื่อนไปวันก่อนหน้าและหาไม่เจอ

## 2.6 · แจ้งเตือน LINE

# เฟส 3 — หลังใช้งานจริงแล้ว

## 3.1 · ทะเบียนเครื่องปรับอากาศ

`/assets` เป็นหน้าเปล่าบอกขอบเขต — schema พร้อมแล้ว (`AcType` มี 10 ประเภท)

1. ทะเบียนเครื่องรายตัว: ยี่ห้อ · รุ่น · BTU · ซีเรียล · ตำแหน่งติดตั้ง
2. ผูกประวัติการซ่อม/ล้างเข้ากับเครื่อง ไม่ใช่แค่กับลูกค้า
3. **ตอบคำถามว่า "เครื่องตัวนี้ซ่อมมากี่ครั้งแล้ว ควรเปลี่ยนหรือยัง"**
4. QR code ติดเครื่อง — ช่างสแกนแล้วเห็นประวัติทันที

## 3.2 · รายงานและสถิติ

`/reports` เป็นหน้าเปล่า — ข้อมูลดิบมีครบแล้วในฐานข้อมูล

1. รายได้แยกตามประเภทงาน / เขต / ช่วงเวลา
2. อัตราการใช้โควตา — ตั้งไว้เหมาะสมหรือยัง วันไหนเต็มบ่อย วันไหนว่างตลอด
3. ผลงานทีมช่าง — จำนวนงาน เวลาเฉลี่ย งานที่ถูกตีกลับ
4. อาการเสียที่พบบ่อย — ป้อนกลับไปที่การสต๊อกอะไหล่
5. ลูกค้าที่เรียกซ้ำบ่อย — สัญญาณว่าซ่อมไม่จบ
6. Export Excel

## 3.3 · เชื่อมกับเว็บเดิม nbcgroup.co.th

ตอนขายรับปากไว้ว่า "เชื่อมต่อกับเว็บไซต์เดิมได้ ไม่ต้องสร้างใหม่"

1. ตรวจโครงสร้างเว็บ WordPress เดิมก่อน
2. **วิธีที่แนะนำ:** ปุ่ม "จองคิวช่าง" บนเว็บเดิม → ลิงก์มาที่ `app.nbcgroup.co.th/booking`
   (ไม่แตะโค้ดเว็บเดิมเลย ปลอดภัยที่สุด)
3. ทำธีมให้กลมกลืน — โทเคนสีจากเว็บบริษัทใส่ไว้แล้ว
   ส้ม `#E4750E` · น้ำเงิน `#2891BD` · กรมท่า `#132945`

## 3.4 · นัด PM อัตโนมัติ

ตารางราคามีรอบ PM 2/3/4 ครั้งต่อปีตามลักษณะการใช้งานอยู่แล้ว

1. ถึงรอบ → สร้างงานอัตโนมัติ เข้าคิวรอยืนยัน
2. แจ้งเตือนลูกค้าล่วงหน้า
3. **กระจายงาน PM ไม่ให้กระจุกวันเดียวกัน** — ต้องเช็คโควตาก่อนสร้าง

## 3.5 · ดูแลระบบระยะยาว

1. สำรองข้อมูลอัตโนมัติ + ทดสอบกู้คืนจริง
2. Monitoring + แจ้งเตือนเมื่อระบบล่ม
3. **วันหยุดนักขัตฤกษ์แบบจันทรคติ** (มาฆบูชา วิสาขบูชา อาสาฬหบูชา เข้าพรรษา)
   ระบบใส่เฉพาะวันหยุดที่วันที่ตายตัว **ไม่เดาวันจันทรคติ** เพราะใส่ผิด
   จะปิดรับงานในวันทำงานโดยไม่มีใครรู้ — ต้องให้ลูกค้ายืนยันรายปี

# สิ่งที่ผู้พัฒนาต่อต้องรู้

- **ค่าที่ลูกค้ายังไม่ยืนยัน เก็บเป็นข้อมูล ไม่ฝังในโค้ด** — ตาราง `AppConfig`
  และหน้า `/settings/assumptions` แก้ได้โดยไม่ต้องแก้โปรแกรม
- **ชื่อตารางเป็น snake_case แต่ชื่อคอลัมน์เป็น camelCase** — SQL ดิบต้องใส่ `"quotes"` ครอบชื่อคอลัมน์
- **`@db.Date` เก็บเป็นเที่ยงคืน UTC** — ใช้ `dateOnly()` เทียบเสมอ
- **`middleware.ts` รันบน Edge runtime** — ห้าม import `node:crypto` หรือ Prisma
- **CSS ที่ต้องชนะ Tailwind ต้องอยู่นอก `@layer`**
- **ห้ามแยกโควตาตามขนาดงาน** — ดูเหตุผลใน `scheduling.prisma:47-53`
  ถ้าแยก วันหนึ่งจะขึ้นว่า "ว่าง" สำหรับงานเล็ก ทั้งที่ช่างถูกจองหมดแล้ว
- **การจองต้องกินโควตาเสมอ** — `createJobFromIntake()` ไม่กินโควตาโดยตั้งใจ
  ห้ามเอาไปใช้กับการจองผ่านเว็บ
