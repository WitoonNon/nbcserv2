## 1.1 · หน้าตั้งค่าโควตา — `/settings/quota` ✅ จุดขายหลัก

**ทำไมต้องมาก่อนหน้าจองคิว:** ปฏิทินจองคิวจะแสดงวันว่างได้ ต้องมี `QuotaDay` ก่อน
ซึ่งเกิดจาก `materialiseQuota()` ซึ่งอ่านจาก `QuotaRule` — ถ้าตั้งกฎไม่ได้ ปฏิทินก็ว่างเปล่า

**ทำไมสำคัญที่สุด:** ลูกค้าถามข้อนี้เป็นคำถามแรกตอนขาย
("กำหนดได้ไหมว่าวันหนึ่งรับได้กี่เคส งานเล็ก 3 งานใหญ่ 1–2")
ถ้าเดโมแล้วโชว์หน้าจอนี้ไม่ได้ = เสียจุดขายหลัก

### ทำแล้ว

| ส่วน | ไฟล์ |
|---|---|
| `createQuotaRule()` · `updateQuotaRule()` · `deactivateQuotaRule()` | `schedule.service.ts` |
| หน้าตารางกฎ + ฟอร์มแก้ไข (ประเภทงาน · เขต · วันในสัปดาห์ · 3 แกน · ช่วงวันที่ · ลำดับ) | `settings/quota/page.tsx` · `QuotaRuleManager.tsx` |
| ปุ่ม **คำนวณปฏิทินใหม่** → `materialiseQuota()` 90 วัน | `settings/quota/actions.ts` |
| **แก้โควตาเฉพาะวันเดียว** ที่ `/schedule` → `setDayCapacity()` | `schedule/actions.ts` · `QuotaCalendar.tsx` |

**กติกาที่ฝังไว้ในโค้ด:**
- กฎที่ไม่กำหนดสักแกนถูกปฏิเสธ — ไม่งั้นวันนั้นจะรับงานไม่จำกัดทั้งที่ดูเหมือนมีเพดาน
- กฎถูก **ปิดการใช้งาน ไม่ลบทิ้ง** — ไม่งั้นจะอธิบายไม่ได้ว่าทำไมวันในอดีตมีความจุเท่านั้น
- ลดเพดานต่ำกว่างานที่จองแล้ว **ไม่ยกเลิกงานเดิม** แค่หยุดขายเพิ่ม (งานสัญญากับลูกค้าไปแล้ว)
- ทุกการแก้รายวันเขียน `QuotaOverrideLog` พร้อมเหตุผลและผู้ทำ

### จุดที่ต้องระวังตอนอธิบายลูกค้า

ระบบ **ไม่แยกช่องตามขนาดงาน** — จงใจ ดูเหตุผลใน `scheduling.prisma:47-53`
"งานใหญ่รับได้ 1–2 เคส" เกิดจากแกน **นาทีทีมช่าง** ไม่ใช่ช่องแยก

ตัวอย่างที่ควรใช้เดโม — ตั้ง `maxTechnicianMinutes = 480`:

| งาน | คำนวณ | ผล |
|---|---|---|
| ล้างแอร์ติดผนัง 30 นาที/เครื่อง | 480 ÷ 30 | รับได้ 16 เครื่อง |
| แอร์ซ่อนในฝ้าใหญ่ 90 นาที/เครื่อง | 480 ÷ 90 | รับได้ 5 เครื่อง |
| งานโรงงาน 40 เครื่อง × 90 นาที | 3,600 > 480 | **เคสเดียวเต็มวัน** |

**คำที่ควรใช้:** "ระบบคิดจากกำลังช่างที่ใช้จริง" — ไม่ใช่ "แยกช่องเล็ก/ใหญ่"

**เกณฑ์ว่าเสร็จ:** แอดมินตั้ง "จันทร์-ศุกร์ ล้าง-PM รับ 8 งาน / 480 นาที" ได้จากหน้าเว็บ
กดคำนวณปฏิทิน แล้วหน้า `/booking` แสดงวันว่างตามนั้นทันที

## 1.2 · หน้าจองคิวลูกค้า — `/booking` ✅

ขั้นตอน: เลือกงาน → เลือกวัน → ยืนยันค่าตรวจเช็ค → จองสำเร็จ

| ทำแล้ว | รายละเอียด |
|---|---|
| เลือกประเภทงาน · ประเภทเครื่อง · จำนวนเครื่อง | ปฏิทินคำนวณใหม่ทุกครั้ง — งาน 40 เครื่องกับ 1 เครื่องมีวันว่างไม่เหมือนกัน |
| ปฏิทิน **แยกรายเดือน + ปุ่มเลือกเดือน** | เปิดเต็ม 90 วันตาม `QUOTA_HORIZON_DAYS` · แต่ละปุ่มบอกว่าเดือนนั้นว่างกี่วัน |
| เลือกวัน → `holdSlot()` | กันคิว 10 นาทีระหว่างกรอกข้อมูล |
| **หน้ายืนยันค่าตรวจเช็ค** | `previewInspectionFee()` · ลูกค้าในสัญญาขึ้น "ยกเว้นตามสัญญา" · **ไม่ติ๊กยอมรับ = จองไม่ได้** |
| ยืนยันจอง → `createJobFromBooking()` | เรียก `bookSlotWithin()` **ในทรานแซกชันเดียวกับการสร้าง Job** |
| หน้าสำเร็จ + ลิงก์ไปหน้าติดตาม | แสดงเลขที่งาน |

> ⚠️ **กติกาที่ห้ามพัง:** `createJobFromIntake()` **ไม่กินโควตา** โดยตั้งใจ (งานรับทางโทรศัพท์
> ให้ผู้จ่ายงานจัดคิวทีหลัง) การจองผ่านเว็บจึงมีเส้นทางของตัวเองคือ `createJobFromBooking()`
> ถ้าเผลอเอา intake มาใช้กับการจองเว็บ = ขายคิวเกิน มี `tests/booking.quota.test.ts` เฝ้าไว้แล้ว

**ทดสอบแล้ว:** จอง 10 รายการพร้อมกันแย่งคิวสุดท้าย → สำเร็จ 1 · งานใหญ่ 3,600 นาทีถูกปฏิเสธ
แม้จำนวนงานยังไม่เต็ม · การจองที่ถูกปฏิเสธไม่ทิ้ง Job ค้างไว้

### บทเรียนจากการ deploy จริง

- **`.vercelignore` จำเป็น** — Vercel ไม่ได้ใช้ `.gitignore` ในการเลือกไฟล์อัปโหลด
  ครั้งแรก `.env` (ที่มีรหัสฐานข้อมูล) ถูกส่งขึ้น build ไปด้วย
- **ตั้ง env ต้องใช้ `vercel env add K E --value V`** — ถ้า pipe ค่าเข้าทาง stdin
  PowerShell จะเติม newline ต่อท้าย ทำให้ deploy ล้มด้วย
  *"CRON_SECRET contains leading or trailing whitespace"*
- **Vercel Hobby รัน cron ได้วันละครั้ง** — `*/10 * * * *` ทำให้ deploy ล้มทันที
- **`Error: fetch failed` ของ CLI มักไม่ใช่ build ล้มจริง** — เป็น log stream หลุด
  ให้เช็คด้วย `vercel ls` ว่าสถานะเป็น `● Ready` หรือไม่

1. **บันทึกร่างไม่ตรวจ ส่งไม่ทิ้งของ** — ช่างกรอกทั้งวัน ถ้าไม่ให้บันทึกเพราะช่องท้าย ๆ ยังว่าง

3. **APPROVED แก้ไม่ได้เลย · SUBMITTED ช่างแก้ไม่ได้** จนกว่าหัวหน้าจะตีกลับ
4. **เปิดใบงานซ้ำต้องได้ร่างเดิม** ไม่ใช่เลขเอกสารใหม่ (เน็ตช้าแล้วกดซ้ำเป็นเรื่องปกติหน้างาน)

### 🐛 บั๊ก 5 ตัวที่แก้ไประหว่างทำข้อนี้ — อย่าให้กลับมา

| # | บั๊ก | เทสต์ที่ล็อกไว้ |
|---|---|---|
| 1 | `seedForms()` เผยแพร่แค่ v1 ทั้งที่โค้ดมี REPAIR v2 — ใบงานจริงจะได้ฟอร์ม**ร่าง** | `workorder.lifecycle` → *freezes the template version* |
| 2 | validator ตารางอะไหล่ตั้งตายตัว `{name, qty, unitPrice}` แต่ฟอร์มจริงมี `รายการ/จำนวน/หน่วย` **ไม่มีช่องราคา** → ทุกแถวถูกปฏิเสธ | `forms.validator` → *follows its declared columns* |

## 2.2 · แนบรูปถ่าย ⬅️ **งานถัดไป**

`StorageAdapter` (`src/lib/storage/index.ts`) ยังเป็น stub — แนะนำ **Supabase Storage**
เพราะใช้โปรเจกต์เดียวกับ DB อยู่แล้ว ไม่ต้องเปิดบัญชีใหม่

1. เขียน adapter จริง (โครง local ⇄ s3 มีแล้ว ไม่ต้องออกแบบใหม่)
2. อัปโหลดจากมือถือ — **ย่อรูปฝั่ง client ก่อนส่ง** (ช่างใช้เน็ตมือถือ รูปจากกล้อง 4–8 MB)
3. จัดหมวดรูปตาม `AttachmentKind` ที่มีแล้ว: ก่อนซ่อม · หลังซ่อม · จุดเสีย · เพลทเครื่อง · ซีเรียล
4. รูปหลายรูปต่อใบงาน

**จุดต่อกับของที่ทำไว้แล้ว:**

- `FormRenderer` case `'photoGroup'` — ตอนนี้วาดกรอบ `+` ว่าง ๆ ไว้ ยังไม่ผูก state
  payload ที่ต้องเขียนคือ **array ของ storage key** (`string[]`) ตามที่ validator รออยู่แล้ว
  ทำข้อนี้เสร็จ **ไม่ต้องแก้ validator และไม่ต้องแก้ `workorder.service.ts` เลย**
- `field.attachmentKind` บอกหมวดรูปมาให้แล้วในตัว schema
- `minCount` มีผลเฉพาะตอน `required: true` (ดูบั๊ก 3 ข้างบน) อย่าเผลอกลับไปบังคับเสมอ
- ตาราง `Attachment` มีอยู่แล้วใน `prisma/schema/media.prisma` ไม่ต้อง migrate เพิ่ม

> ⚠️ ถ้าใช้ Supabase Storage อย่าใช้ bucket แบบ public กับรูปหน้างานลูกค้า —
> ชื่อไฟล์เดาได้เท่ากับเปิดให้คนนอกดูรูปบ้านลูกค้า ใช้ signed URL

## 2.3 · ลายเซ็น

1. Canvas เซ็นด้วยนิ้วบนมือถือ
2. บันทึก `Signature.payloadHash` = SHA-256 ของเนื้อหาตอนเซ็น
   **นี่คือความต่างระหว่าง "รูปลายเซ็น" กับ "หลักฐาน"** — แก้ทีหลังจะตรวจจับได้
3. 3 บทบาท: ลูกค้า · ช่าง · หัวหน้างาน (enum `SignerRole` มีแล้ว)

**ฟังก์ชัน hash เขียนไว้ให้แล้ว** — `payloadHash()` ใน `workorder.service.ts`
เรียงคีย์ก่อน stringify เสมอ ดังนั้นบันทึกซ้ำโดยเนื้อหาไม่เปลี่ยน จะไม่ถูกมองว่าถูกแก้
(มีเทสต์ล็อกไว้ 3 ข้อใน `workorder.lifecycle.test.ts`)

`FormRenderer` case `'signature'` ยังเป็นกล่อง "เซ็นที่นี่" เปล่า ๆ
payload ที่ต้องเขียนคือ **string เดียว** (storage key ของรูปลายเซ็น) ตามที่ validator รออยู่

# สิ่งที่ผู้พัฒนาต่อต้องรู้

- **ค่าที่ลูกค้ายังไม่ยืนยัน เก็บเป็นข้อมูล ไม่ฝังในโค้ด** — ตาราง `AppConfig`
  และหน้า `/settings/assumptions` แก้ได้โดยไม่ต้องแก้โปรแกรม
- **ชื่อตารางเป็น snake_case แต่ชื่อคอลัมน์เป็น camelCase** — SQL ดิบต้องใส่ `"quotes"` ครอบชื่อคอลัมน์
- **`@db.Date` เก็บเป็นเที่ยงคืน UTC** — ใช้ `dateOnly()` เทียบเสมอ
- **`middleware.ts` รันบน Edge runtime** — ห้าม import `node:crypto` หรือ Prisma
- **CSS ที่ต้องชนะ Tailwind ต้องอยู่นอก `@layer`**
- **ห้ามแยกโควตาตามขนาดงาน** — ดูเหตุผลใน `scheduling.prisma:47-53`
  ถ้าแยก วันหนึ่งจะขึ้นว่า "ว่าง" สำหรับงานเล็ก ทั้งที่ช่างถูกจองหมดแล้ว
- **การจองต้องกินโควตาเสมอ** — `createJobFromIntake()` ไม่กินโควตาโดยตั้งใจ
  ห้ามเอาไปใช้กับการจองผ่านเว็บ ใช้ `createJobFromBooking()` แทน
  (`tests/booking.quota.test.ts` คุมไว้แล้ว)
- **`where: { field: undefined }` ใน Prisma แปลว่า "ไม่กรองเลย" ไม่ใช่ "ไม่ตรงอะไร"**
  เทสต์ที่ teardown ด้วย `deleteMany({ where: { zoneId } })` โดย `zoneId` ยังไม่ถูกเซ็ต
  จะลบ **ทุกแถวในตาราง** — เคยเกิดจริง ปฏิทินโควตาหายทั้งตาราง
  ตอนนี้ teardown ทั้งสองไฟล์มี `if (zoneId)` ครอบแล้ว
- **`npm run dev` วัด performance ไม่ได้** — ต้อง `npm run build && npm run start`
